# LURK — сервер

FastAPI, SQLAlchemy, PostgreSQL и Alembic. Инструкция ниже рассчитана на Windows PowerShell и Python 3.13; команды запускайте из папки сервера.

## 1. Зависимости

```powershell
cd C:\Users\sutir\PycharmProjects\HideAndSeek
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Если `.venv` уже существует, повторно создавать её не нужно. Если `py` не установлен, используйте `python -m venv .venv` с Python 3.13. Версии непосредственных зависимостей зафиксированы в `requirements.txt` и `requirements-dev.txt`.

## 2. Отдельная база разработки

Через pgAdmin или `psql` создайте **новую пустую** БД PostgreSQL, например `lurk_dev`, и отдельную учётную запись с правами создавать таблицы и типы в этой БД. Для тестов используйте другую пустую БД, например `lurk_test`: некоторые интеграционные тесты создают игровые данные.

В каждом окне PowerShell задайте адрес (подставьте свои данные; пароль в URL при необходимости закодируйте в percent-encoding):

```powershell
$env:DATABASE_URL = "postgresql+asyncpg://lurk:YOUR_PASSWORD@localhost:5432/lurk_dev"
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic check
```

`.env.example` — только образец: проект не загружает файл `.env` автоматически. Пароль в Git добавлять нельзя. Переменная `DATABASE_URL` обязательна как для сервера, так и для Alembic. Начальная миграция рассчитана на **пустую** БД.

**Существующая база:** не запускайте на ней `upgrade`, `stamp` или `downgrade` вслепую. Она могла быть создана старым `create_all` и отличаться от модели. Сначала сделайте резервную копию и отдельно сравните схему с начальной миграцией; только после проверки можно выбрать способ переноса. Сам запуск сервера больше не создаёт и не изменяет таблицы автоматически.

В рамках первичной проверки создана отдельная локальная БД `lurk_stage1_b87368db`; она не является основной или автоматически настроенной базой проекта. Данные старой БД не изменялись.

## 3. Запуск API

```powershell
# В этом же окне PowerShell, где задан DATABASE_URL:
.\.venv\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000
```

Проверка: `http://127.0.0.1:8000/` и `http://127.0.0.1:8000/docs`. Эмулятор Android обращается к компьютеру по `10.0.2.2:8000`. Для физического телефона и сервера в одной сети запустите Uvicorn с `--host 0.0.0.0`, настройте брандмауэр только для доверенной сети и задайте клиенту локальный IP компьютера. Не открывайте разработческий сервер в интернет без защиты.

Для обратного прокси можно установить `$env:PUBLIC_BASE_URL = "https://your-domain.example"`: сервер использует этот адрес при формировании `ws_url` для подключения игрока. Без него адрес берётся из входящего запроса. На постоянном сервере настройте HTTPS/WSS, обратный прокси с поддержкой WebSocket, секреты и резервное копирование. Доступ к базе извне не открывайте.

## Базовый сценарий и ограничения

Для старта нужны минимум два готовых игрока: хотя бы один ищущий и один прячущийся. Ищущий отправляет запрос о поимке, прячущийся подтверждает или отклоняет его. Запрос действует две минуты и хранится в памяти одного процесса; при перезапуске сервера его потребуется отправить заново. Текущая версия предназначена для локальной проверки: токены участников, устойчивое восстановление таймеров и полный сценарий переподключения ещё не реализованы. **Не публикуйте её для реальных игр** до решения вопросов безопасности и проверки на устройствах.

Обычные сообщения и снимки игры больше не рассылают точные координаты других игроков, но это не полноценная защита: сервер ещё не проверяет подлинность участника по секретному токену. Урон за выход из зоны сейчас начисляется при получении обновления координат, поэтому зависит от частоты сообщений; эта механика требует дальнейшей доработки. Способности и события также не прошли сквозную проверку.

После обновления способностей создайте новую игру: участникам выдаётся набор выбранной роли при входе и смене роли в лобби. Щит поглощает один удар; разведка и сканирование показывают координаты на ограниченное время только активировавшему их игроку. Для персональной бомбы и ловушки выбирается точка на карте; капкан и укрытия создаются около игрока. Время перезарядки и число использований проверяет сервер. Ловушка уведомляет попавшего игрока и ищущих, но пока **не препятствует физическому выходу** из зоны и не назначает за него наказание; правила нарушения нужно определить отдельно. После потери соединения полное восстановление оставшихся использований и таймеров пока не гарантируется. Результаты проверки способностей в реальной игре на телефонах и событиях ещё требуют отдельного подтверждения.

## Второй игрок из терминала

`tools/test_player.py` присоединяется к **уже созданной** комнате как настоящий игрок. Нужны запущенный сервер и зависимости из `requirements-dev.txt`. Клиент обращается к локальному серверу напрямую; для работы вместе с телефоном через ngrok создайте комнату на телефоне, а сервер и тестовый клиент запустите на одном компьютере.

1. Создайте комнату на Android и скопируйте её шестизначный код.
2. Выберите на карте безопасную область вокруг известной тестовой точки. В примере ниже указаны условные координаты; замените их координатами внутри **вашей** игровой зоны. Вводите десятичные числа с точкой, сначала широту, затем долготу.
3. Откройте **второй** терминал в папке сервера и выполните:

   ```powershell
   cd C:\Users\sutir\PycharmProjects\HideAndSeek
   .\.venv\Scripts\python.exe tools\test_player.py --code ABC123 --name Test --lat 55.75 --lng 37.61
   ```

   Замените `ABC123` на код комнаты. Для сервера не на этом компьютере добавьте `--server https://адрес-сервера/`.
4. После подключения программа покажет роли и игроков. Команды вводятся **без слэша**: `roles`, `role 1` или `role 2`, `ready`, `unready`, `players`, `state`, `catch 1`, `accept`, `reject`, `location 55.75 37.61`, `help`, `quit`. Номера берутся из последнего выведенного списка. Если состав изменился, введите `state`.

Например, чтобы проверить поимку, назначьте тестовому игроку роль прячущегося, а телефону — ищущего. Введите `ready`, подтвердите готовность на телефоне и дождитесь конца времени на прятки. Когда телефон отправит запрос о поимке, в терминале появится приглашение: введите `reject` для отказа или `accept` для подтверждения. Запрос действует 2 минуты. Для теста в обратную сторону выберите тестовому игроку роль ищущего, введите `players`, затем `catch НОМЕР` прячущегося.

Скрипт не подделывает GPS Android и не проверяет интерфейс телефона. Он сохраняет игрока в базе и не удаляет игровую сессию при выходе, поэтому применяйте его к тестовой базе. `quit` закрывает подключение, но не удаляет игрока. При выходе из игры или отзывах запросов автоматическое переподключение не реализовано. Если все игроки оказались готовы до выбора разных ролей, сервер откажет в старте: скорректируйте роли и при необходимости заново переключите готовность.

Для проверки способностей доступны команды `ability SHIELD`, `ability INTEL`, `ability SCAN`, `ability SNARE`, `ability SAFE_HOUSE`, `ability SAFE_MANSION`, а также `ability PERSONAL_BOMB 55.75 37.61` и `ability TRAP 55.75 37.61` с координатами точки. Способность должна быть выдана выбранной роли при создании новой игры; координаты выбирайте внутри игровой зоны. Команда `location` имитирует передвижение Python-игрока, а не телефона.

## Важное о секретах

В прежних версиях проекта пароль БД находился в исходном коде. Удаление его из текущего файла не удаляет его из истории Git. Если репозиторий был опубликован или пароль использовался где-то ещё, смените пароль и проверьте доступы; не публикуйте старую историю без оценки риска.
